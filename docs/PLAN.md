# Транслифт — план реализации

Требования описаны в [TZ.md](../TZ.md). Здесь записаны решения по стеку, структура репозитория, модель данных и график работ.

## Стек

| Слой                    | Решение                                                                      |
| ----------------------- | ---------------------------------------------------------------------------- |
| Монорепозиторий         | pnpm workspaces: `backend/`, `frontend/`                                     |
| Линтер и форматирование | Biome, один конфиг в корне                                                   |
| Backend                 | NestJS + TypeScript                                                          |
| БД                      | PostgreSQL 17 + Prisma 7 (driver adapter `@prisma/adapter-pg`)               |
| Файлы                   | S3-совместимое хранилище: SeaweedFS на том же сервере (было MinIO, см. ниже) |
| Excel                   | ExcelJS на сервере заполняет файл-образец заказчика                          |
| Frontend                | React + Vite + TypeScript, архитектура FSD в упрощённом виде                 |
| UI                      | shadcn/ui, пресет Nova (Radix + Tailwind 4); drawer — vaul                   |
| Данные на фронте        | TanStack Query                                                               |
| Роутинг                 | React Router 8                                                               |
| Контракт API            | OpenAPI из NestJS (`@nestjs/swagger`), типы для фронта генерируются из схемы |
| Развёртывание           | docker compose: app, postgres, seaweedfs, caddy на VPS в РФ                  |

Почему не Firebase: 152-ФЗ требует хранить персональные данные в РФ, российское юрлицо не может оплатить Google Cloud, а по ТЗ заказчик сам владеет инфраструктурой и делает бэкапы.

## Нагрузка

- Пользователи: 10–30 человек.
- Объекты: десятки или сотни в год.
- Запросы: единицы в минуту.
- Фото: 30–40 на объект, около 300 КБ после сжатия на телефоне. Получается 2–5 ГБ в год.

Фото — единственный ресурс, который растёт. Поэтому нужен экран «Хранилище» (см. ниже).

## Структура репозитория

```
translift/
├── backend/            NestJS
│   ├── prisma/         schema.prisma, миграции, seed
│   └── src/
│       ├── modules/    auth, users, brigades, contracts, templates, objects,
│       │               marks, files, claims, finance, reports, notifications, storage
│       └── common/     guards, декораторы ролей, prisma, s3
├── frontend/           React + Vite
│   └── src/
│       ├── app/        провайдеры, роутер, стили
│       ├── pages/      экраны (dashboard, objects, object-card, foreman, claims, reports, refs, storage)
│       ├── features/   действия пользователя (mark-stage, assign-brigade, upload-photo…)
│       ├── entities/   доменные сущности: типы, api-хуки, карточки (object, stage, brigade…)
│       └── shared/     ui (shadcn), api-клиент, lib, config
├── docker-compose.yml  postgres + seaweedfs для локальной разработки, профиль app — всё приложение
├── biome.json
└── docs/
```

Упрощённый FSD:

- слоя `widgets` нет, крупные блоки живут в `pages/<page>/ui`;
- `processes` не используем;
- импорты идут только сверху вниз: `app → pages → features → entities → shared`.

## Модель данных (черновик)

- **User**: почта (она же логин), хеш пароля, ФИО, роль (`ADMIN`, `MANAGER`, `FOREMAN`, `FINANCE`), активен, бригада.
- **Brigade**: название, бригадир (`User`), численность.
- **Customer**: заказчик или генподрядчик.
- **Contract**: номер, дата, заказчик, ответственный в отчёте, ссылка для фотоотчётов.
- **StageTemplate**: тип работ — `REPLACEMENT` (замена) или `NEW_BUILDING` (новостройка).
- **TemplateStage**: шаблон, порядок, полное название (как в отчёте), короткое название, контрольный %, нужно ли фото.
- **LiftObject** (объект — дом по адресу): адрес полный и короткий, договор, срок по договору, бригада, архив. Документы и финансы — общие на объект.
- **Lift** (лифт объекта, минимум один):
  - подъезд («Подъезд 1») и название в подъезде («Лифт 2», «Грузовой»); у единственного лифта подпись не показывается; порядок;
  - этажность, грузоподъёмность, сведения о лифте, тип работ (шаблон), своя бригада (пусто — бригада объекта);
  - текущий этап, статус поставки оборудования с плановой и фактической датой;
  - контрольные даты: плановое начало, открытие, ПТО, декларация, ввод в эксплуатацию, комиссия, КС-2/КС-3.
- **StageMark**: объект, лифт, этап, дата и время, исполнитель, комментарий. Отметки не удаляются, отмена записывается в журнал.
- **File**:
  - ключ в S3, тип (`PHOTO`, `DOCUMENT`), размер, mime, превью;
  - привязка к объекту, отметке или рекламации;
  - `takenAt`, `deletedAt`.
- **Claim** (рекламация): объект, лифт (необязательно), дата, изготовитель/поставщик, тип (брак, недокомплект, несоответствие), описание, статус, комментарии, файлы.
- **ObjectFinance**: номер и дата договора (по умолчанию — из «Сведений»), сумма по договору, закрыто работ по актам.
- **FinanceEntry** — журнал денег объекта: платежи заказчика, доп. соглашения (меняют сумму для заказчика, могут быть со знаком минус), расходы со статьёй (оборудование, работы, прочее). Сумма для заказчика = договор + доп. соглашения; остаток = сумма для заказчика − платежи; доходность = сумма для заказчика − расходы. Формулы согласует заказчик.
- **AuditLog**: кто, когда, сущность, что изменилось. Из него строятся история объекта и журнал.
- **Notification**: событие или риск в интерфейсе, кому адресовано, прочитано ли.

Права:

- роль проверяется на сервере;
- финансовые поля отдаются только ролям `ADMIN`, `MANAGER` и `FINANCE`;
- бригадир видит объекты своей бригады и объекты, где его бригада ведёт отдельный лифт; отмечает этапы только у своих лифтов.

## Хранилище и очистка (экран администратора)

Требование команды, в ТЗ его нет: администратор видит, сколько занято, и сам чистит старые данные.

- **Заполненность:**
  - размер БД (`pg_database_size`) и крупнейших таблиц;
  - объём S3: всего, по типам файлов, по объектам, по месяцам;
  - свободное место на диске сервера.
- **Очистка фото (в первую очередь):**
  - фильтры: объекты в статусе «сдан» старше N месяцев, период, объект;
  - предпросмотр: сколько файлов и мегабайт освободится;
  - режимы: удалить оригиналы и оставить превью, или удалить полностью;
  - подтверждение и запись в журнал.
- **Прочее:** очистка прочитанных уведомлений и старых записей журнала старше N месяцев.
- **Сжатие на входе:** фото сжимаются на телефоне до ~1600px JPEG, на сервере создаётся превью ~400px.

## Полировка интерфейса (идеи команды)

Сверх ТЗ, делаем после основных функций недели 4 или параллельно, если останется время.

- [x] **Лоадер «едущий лифт»**: кабина ездит по шахте вверх-вниз. Используется при загрузке страницы и долгих действиях (выгрузка отчёта, загрузка фото).
- [x] **Скелетоны по форме контента** вместо серых прямоугольников: строки таблицы реестра, карточки объектов, шахты на сводке, лестница этапов.

- [x] **Фавиконка и логотип**: знак — строгая голубая «Т» на стальном блоке (шов на ножке — стык дверей кабины), свой SVG; фирменные цвета — переменные `--brand*` в `index.css`. Иконки 192/512 и apple-touch-icon для PWA.
- [x] **PWA, минимальная версия** (см. ниже).

### PWA

Ярлык «на рабочий стол» без PWA открывает обычную вкладку браузера с адресной строкой. Если состояние вкладки сбросилось, она грузится заново.

PWA — это manifest и service worker. Что они дают:

- запуск в отдельном окне без панелей браузера, со своей иконкой и заставкой — выглядит как приложение;
- оболочка приложения (JS, CSS, шрифты) кешируется: повторный запуск мгновенный даже на слабом 3G, после выкладки новой версии приложение обновляется само;
- камера и загрузка фото работают так же, как в браузере.

Это не «мобильное приложение для установки из магазинов», так что в рамки ТЗ укладывается.

План:

1. **Минимум (берём, ~0,5 дня):** `vite-plugin-pwa`, manifest (название, иконки, `display: standalone`, цвет темы), кеш оболочки, подсказка «Установите на телефон» на экране бригадира. API и фото не кешируем: данные всегда свежие.
2. **Офлайн-очередь отметок (опционально, после приёмки, ~2–3 дня):** бригадир в подвале или шахте без сети отмечает этап, фото и отметка лежат в IndexedDB и отправляются при появлении сети. Это реальная польза на объектах, но сюда входит синхронизация и конфликты, поэтому делаем только по согласованию.
3. **Push-уведомления: не делаем без отдельного соглашения.** По ТЗ внешние каналы уведомлений идут отдельно. На iOS push работает только у установленного PWA и только с iOS 16.4.

## Сделано сверх плана

- **Объекты с несколькими лифтами** (согласовано с командой, у заказчика — вопрос 5):
  - объект — дом: договор, адрес, срок, документы и финансы общие; у каждого лифта свои характеристики, этапы, поставка, даты и, при необходимости, своя бригада;
  - объект с одним лифтом выглядит и заполняется как раньше; при создании можно сразу указать подъезд и число лифтов в нём («Лифт 1…N»);
  - «+ Лифт» добавляет лифты в подъезд — выбранный из заведённых или новый; лифты подъезда без названия нумеруются «Лифт 1, 2…», единственный лифт подъезда при добавлении второго становится «Лифт 1»;
  - в таблице «Все лифты» лифты сгруппированы под общей шапкой подъезда;
  - на странице объекта переключатель «Все лифты · Подъезд 1 · …»: «Все» — таблица этапы × лифты (нажать рамку следующего этапа — отметить его у этого лифта), лифт — его этапы, фото, даты;
  - этапы отмечаются у каждого лифта отдельно, групповой отметки нет (решение команды);
  - готовность объекта — средняя по лифтам, состояние и текущий этап — по отстающему; в сводке шахты лифтов одного дома стоят одним блоком, в списках — полоска на каждый лифт; счётчики сводки — по лифтам;
  - отчёт генподрядчику — строка на лифт (адрес + название), отчёт по объекту — разделы по лифтам; импорт понимает колонку «Лифт».
- **Финансы переделаны** (по замечаниям команды, вместо полей ТЗ «стоимость оборудования от завода» и «стоимость для заказчика» — `TODO(заказчик)`: подтвердить):
  - договор подставляется из «Сведений», номер и дату можно сменить;
  - доп. соглашения, платежи и расходы — списками с итогами; у каждого поля и итога значок «?» с пояснением;
  - доходность объекта и процент; ушёл в минус — красная плашка и уведомление руководителям; в карточке договора и заказчика — доходность и число объектов в минусе; в отчётах — расходы и доходность;
  - при переходе: «стоимость оборудования» стала расходом «Оборудование», оплата — платежом; «стоимость для заказчика» перенесена в сумму договора, только если та была пустой.
- **Селекты с поиском.** Все выпадающие списки (`SimpleSelect`) с полем поиска: печатаете — список фильтруется, пролистать тоже можно.
- Правки после второго теста (ноябрь 2026):
  - **Вход только по почте.** Логин убран, почта обязательна и уникальна; текущим сотрудникам без почты проставлено `логин@user.ru`.
  - **Плановые даты этапов.** У этапа в справочнике есть «дней по плану», полное название редактируется. План считается от «Начала работ» объекта (поле в форме объекта). В «Ходе работ» и «Сведениях» видны план, факт и отклонение. Стартовые длительности — оценка, `TODO(заказчик)`.
  - **Договоры и заказчики.** У договора и заказчика своя страница: объекты списком, деньги по «Финансам» (их видят администратор, руководитель и финансист). В справочниках добавлена вкладка «Заказчики».
  - **Длинные списки.** Объекты, рекламации, уведомления и история объекта грузятся с сервера порциями по 30 при прокрутке, с «Загружаем ещё…» и «Показано N из M». Остальные таблицы рисуются порциями. Объекты по умолчанию идут «сначала новые», можно выбрать «по сроку».
  - **Окна.** На телефоне — шторка снизу, на компьютере — крупный блок по центру. Рекламация открывается на своей странице.
  - **Черновики фото.** Фото из несохранённой отметки этапа удаляются сразу, а забытые — ночью.
  - **Дизайн.** Иконки Phosphor, системный шрифт (SF на Apple), радиусы острее, основной цвет — фирменный стальной синий, строгие маркеры этапов.

- По замечаниям после теста: «Создать» прямо в селектах — договор и бригада из формы объекта, заказчик из договора, бригадир из бригады (окна открываются одно поверх другого, созданное сразу выбирается). Форма объекта больше не подставляет договор сама и показывает актуальные договор и бригаду. В «Финансах» действует договор из «Сведений», пока не указан свой номер (`TODO(заказчик)`: бывает ли отдельный договор по деньгам). Кнопка «Архив» в списке объектов. Логотип ведёт на главную. Место на диске проверяется каждый час.

- Вторая очередь готовности к продакшену: CSP и Permissions-Policy в Caddy; блокировка входа на 15 минут после 10 неверных паролей (уведомление администраторам, «Снять блокировку» в карточке); ночная чистка сессий и старых уведомлений, предупреждение о месте на диске; `pnpm audit` чист (overrides в `pnpm-workspace.yaml`, `shadcn` — в devDependencies); CI в GitHub Actions — линтер, типы, unit, e2e с PostgreSQL и SeaweedFS, сборка Docker-образов.

- **Замена MinIO на SeaweedFS (ноябрь 2026).** Образы бесплатной версии MinIO исчезли из Docker Hub и quay.io — на новый сервер его не поставить. SeaweedFS (Apache 2.0) говорит по тому же протоколу S3, код приложения не менялся: только compose, скрипты копий и создание бакета при запуске backend. Локальные файлы перенесены.

- Готовность к продакшену: загружаемые документы — только из белого списка расширений (тип определяется по расширению, не по браузеру), в браузере открываются только фото и PDF, всё остальное — на скачивание; ответы с файлами в `CSP: sandbox`. Версии образов закреплены, логи контейнеров ограничены, Swagger на сервере выключен.

- Уведомления: открываются для просмотра, из окна — переход в нужный раздел (объект, рекламация, «Пользователи»). Прочитано / не прочитано у каждого своё, можно вернуть «не прочитано»; вкладка «Непрочитанные», группировка по дням.

- Запуск всего приложения в Docker одной командой (`pnpm app:up`, http://localhost:8080) — для показа и проверки без настройки Node.

- Профиль пользователя: правка ФИО и телефона, смена пароля, выход на других устройствах, выход с подтверждением.
- Адаптив: на телефоне таблицы заменены карточками (`DataList`), горизонтальной прокрутки страниц нет. Шапка и меню неподвижны, прокручивается только контент.
- Тёмная, светлая и системная тема.
- Ленивая загрузка страниц: бригадиру с телефона не грузится код сводки, справочников и отчётов.

## Решения без ответа заказчика

Заказчик занят, поэтому решаем сами и правим по обратной связи. Места в коде помечены `// TODO(заказчик): …`.

| Вопрос                | Решение                                                                                                                                                        |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Шаблон новостройки    | Копия шаблона замены. Администратор правит названия и проценты в справочнике                                                                                   |
| Остаток задолженности | `стоимость для заказчика − поступившая оплата`; если стоимость пуста — `сумма договора − оплата`                                                               |
| Видимость финансов    | `ADMIN` и `FINANCE` видят и правят; `MANAGER` видит; `FOREMAN` не видит                                                                                        |
| Отчёт генподрядчику   | Форма ФКР «Еженедельный отчёт об исполнении договора» из демо, 13 колонок                                                                                      |
| Объект                | Объект — дом, внутри один или несколько лифтов со своими этапами. Финансы — на объект                                                                          |
| Изменение процентов   | Пересчитываются все объекты, как в демо: процент берётся из справочника при каждом расчёте                                                                     |
| Отметки этапов        | Можно отметить сразу несколько этапов (пропущенные отмечаются той же датой). Дата — сегодня или до 7 дней назад. Отменить последнюю отметку может руководитель |
| Фото                  | Обязательно там, где в справочнике стоит флажок (сейчас везде), нужно хотя бы одно                                                                             |
| Поставка оборудования | `не заказано → заказано → поставлено`, плановая и фактическая дата                                                                                             |
| Контрольные даты      | Ставятся сами при отметке этапа (ПТО, комиссия, КС), руководитель правит вручную                                                                               |
| Рекламации            | Статусы `новая → на рассмотрении → принята / отклонена → закрыта`; поставщик — свободный текст с подсказками из прошлых значений                               |
| «Требуют внимания»    | Как в демо: срок прошёл; до срока ≤21 дня и <80%; отставание от линейного графика >20 п.п.; нет отметок ≥7 дней; нет бригады                                   |
| Хранение фото         | Без автоудаления. Администратор чистит вручную на экране «Хранилище»                                                                                           |
| Пользователи          | Почта для входа у каждого бригадира, бригада привязана к бригадиру                                                                                             |

## Как фронт получает типы API

Схемы запросов и ответов лежат в `backend/src/contracts/` — это чистый TypeScript + Zod, без импортов из Nest и Prisma. Backend валидирует ими запросы (`@Body({ schema })`) и строит OpenAPI. Frontend импортирует их через алиас `@contracts` — одни и те же схемы проверяют формы и описывают ответы.

## Фото и файлы

- Телефон сжимает фото до ~1600px JPEG и делает превью ~400px, загружает оба (`POST /api/files`, multipart).
- Файлы идут **через backend**, без presigned-ссылок: он проверяет права (бригадир — только свои объекты) и отдаёт файл из S3 потоком с долгим кешем. Хранилище наружу не открыто.
- Отметка этапа ссылается на уже загруженные фото (`photoIds`). Фото, загруженные без отметки, — кандидаты на очистку на экране «Хранилище».

## Авторизация

Своя, без сторонних библиотек: почта и пароль (scrypt), сессия в httpOnly cookie, в БД хранится только SHA-256 токена. Глобальный guard закрывает все маршруты, `@Public()` открывает, `@Roles(...)` ограничивает по ролям. Вход ограничен по частоте (`@nestjs/throttler`).

### Пользователи и пароли

Раздел «Пользователи» (только администратор): завести сотрудника, задать почту (обязательна, по ней вход), роль, телефон, сбросить пароль, отправить в архив.

- **Вход только по почте** (решение после теста, ноябрь 2026). Почта обязательна и уникальна, телефон — просто контакт. Сотрудникам без почты при переходе проставлено `логин@user.ru` — администратор заменит на настоящую.
- **Телефон** — поле с маской `+7 900 123-45-67`: «8…», «7…» и «9…» сразу превращаются в «+7…», вставка в любом виде тоже; Backspace перескакивает разделители. Проверка — `libphonenumber-js` (по умолчанию Россия, другие страны — с «+»). В базе E.164 `+79001234567`.
- **Почта** — проверка формата, хранится в нижнем регистре.
- **Архив и удаление** (сотрудники и бригады). Удалить совсем можно только запись без истории — заведённую по ошибке. Остальное — в архив: пропадает из списков и выбора, история остаётся, можно вернуть. Сотрудник в архиве сразу выходит из системы, его бригада освобождается. Бригаду с объектами в работе в архив не отправить — сначала переназначить объекты.

- **Пароль от администратора всегда временный.** При создании его можно ввести или оставить пустым — система придумает читаемый вида `k7mp-x3qa-9fde` (без похожих символов, удобно продиктовать по телефону). Показывается один раз, с кнопкой «Скопировать».
- **Первый вход.** С временным паролем пускает только на экран «Придумайте свой пароль» — это проверяет и сервер (guard отвечает 403 на всё, кроме `me`, `profile`, `password`, `logout`).
- **Забыли пароль?** Почты и СМС нет: внешние рассылки вне ТЗ, у бригадиров часто нет рабочей почты. Кнопка на экране входа отправляет запрос администраторам: уведомление и жёлтый блок «Просят новый пароль» вверху раздела. Администратор звонит сотруднику и одной кнопкой выдаёт новый временный пароль. Ответ на запрос одинаковый для любой почты (по нему нельзя узнать, есть ли пользователь), частота ограничена, повторы в течение часа не плодят уведомления.
- **Сброс** выкидывает сотрудника со всех устройств.
- **Если пароль забыл единственный администратор** — на сервере: `docker compose exec backend npx prisma db seed` с новым `SEED_ADMIN_PASSWORD` (см. DEPLOY.md).

### На согласование (вне ТЗ, отдельная оценка)

- **Разделы демо «Комплектация», «Сметы», «Обслуживание лифтов»** — ТЗ прямо исключает их из объёма («Что не входит в объём работ»: покомпонентный учёт комплектации, сметы, ТО). Из комплектации по ТЗ сделан статус поставки оборудования на объекте (`не заказано → заказано → поставлено`, плановая и фактическая дата, риск «поставка опаздывает»). Поштучный учёт (направляющие, двери, кабина, лебёдка… со статусами «заказано → на складе → смонтировано») — отдельная оценка, ~3–4 дня.

- **Офлайн-очередь отметок и фото для бригадира (~2–3 дня).** Без связи (подвал, шахта) отметка с фото сохраняется на телефоне (IndexedDB) и отправляется сама при появлении сети; бригадир видит «ожидает отправки». Нужны правила для конфликтов: например, этап за это время отметил руководитель. Предложить заказчику после приёмки.
