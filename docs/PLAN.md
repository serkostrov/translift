# Транслифт — план реализации

Требования описаны в [TZ.md](../TZ.md). Здесь записаны решения по стеку, структура репозитория, модель данных и график работ.

## Стек

| Слой                    | Решение                                                                      |
| ----------------------- | ---------------------------------------------------------------------------- |
| Монорепозиторий         | pnpm workspaces: `backend/`, `frontend/`                                     |
| Линтер и форматирование | Biome, один конфиг в корне                                                   |
| Backend                 | NestJS + TypeScript                                                          |
| БД                      | PostgreSQL 17 + Prisma 7 (driver adapter `@prisma/adapter-pg`)               |
| Файлы                   | S3-совместимое хранилище: MinIO на том же сервере                            |
| Excel                   | ExcelJS на сервере заполняет файл-образец заказчика                          |
| Frontend                | React + Vite + TypeScript, архитектура FSD в упрощённом виде                 |
| UI                      | shadcn/ui, пресет Nova (Radix + Tailwind 4); drawer — vaul                   |
| Данные на фронте        | TanStack Query                                                               |
| Роутинг                 | React Router 8                                                               |
| Контракт API            | OpenAPI из NestJS (`@nestjs/swagger`), типы для фронта генерируются из схемы |
| Развёртывание           | docker compose: app, postgres, minio, caddy на VPS в РФ                      |

Почему не Firebase: 152-ФЗ требует хранить персональные данные в РФ, российское юрлицо не может оплатить Google Cloud, а по ТЗ заказчик сам владеет инфраструктурой и делает бэкапы.

## Нагрузка

- Пользователи: 10–30 человек.
- Объекты: десятки или сотни в год.
- Запросы: единицы в минуту.
- Фото: 30–40 на объект, около 300 КБ после сжатия на телефоне. Получается 2–5 ГБ в год.

Фото — единственный ресурс, который растёт. Поэтому нужен экран «Хранилище» (см. ниже).

## Структура репозитория

```
translift/
├── backend/            NestJS
│   ├── prisma/         schema.prisma, миграции, seed
│   └── src/
│       ├── modules/    auth, users, brigades, contracts, templates, objects,
│       │               marks, files, claims, finance, reports, notifications, storage
│       └── common/     guards, декораторы ролей, prisma, s3
├── frontend/           React + Vite
│   └── src/
│       ├── app/        провайдеры, роутер, стили
│       ├── pages/      экраны (dashboard, objects, object-card, foreman, claims, reports, refs, storage)
│       ├── features/   действия пользователя (mark-stage, assign-brigade, upload-photo…)
│       ├── entities/   доменные сущности: типы, api-хуки, карточки (object, stage, brigade…)
│       └── shared/     ui (shadcn), api-клиент, lib, config
├── docker-compose.yml  postgres + minio для локальной разработки
├── biome.json
└── docs/
```

Упрощённый FSD:

- слоя `widgets` нет, крупные блоки живут в `pages/<page>/ui`;
- `processes` не используем;
- импорты идут только сверху вниз: `app → pages → features → entities → shared`.

## Модель данных (черновик)

- **User**: логин, хеш пароля, ФИО, роль (`ADMIN`, `MANAGER`, `FOREMAN`, `FINANCE`), активен, бригада.
- **Brigade**: название, бригадир (`User`), численность.
- **Customer**: заказчик или генподрядчик.
- **Contract**: номер, дата, заказчик, ответственный в отчёте, ссылка для фотоотчётов.
- **StageTemplate**: тип работ — `REPLACEMENT` (замена) или `NEW_BUILDING` (новостройка).
- **TemplateStage**: шаблон, порядок, полное название (как в отчёте), короткое название, контрольный %, нужно ли фото.
- **LiftObject**:
  - адрес полный и короткий, этажность, грузоподъёмность, тип работ (шаблон), договор, срок по договору, бригада;
  - текущий этап, статус поставки оборудования с плановой и фактической датой;
  - контрольные даты: открытие, ПТО, декларация, ввод в эксплуатацию, комиссия, КС-2/КС-3.
- **StageMark**: объект, этап, дата и время, исполнитель, комментарий. Отметки не удаляются, отмена записывается в журнал.
- **File**:
  - ключ в S3, тип (`PHOTO`, `DOCUMENT`), размер, mime, превью;
  - привязка к объекту, отметке или рекламации;
  - `takenAt`, `deletedAt`.
- **Claim** (рекламация): объект, дата, изготовитель/поставщик, тип (брак, недокомплект, несоответствие), описание, статус, комментарии, файлы.
- **ObjectFinance**: сумма договора, стоимость оборудования от завода, стоимость для заказчика, закрытые работы, оплата. Остаток считается формулой, формулу согласует заказчик.
- **AuditLog**: кто, когда, сущность, что изменилось. Из него строятся история объекта и журнал.
- **Notification**: событие или риск в интерфейсе, кому адресовано, прочитано ли.

Права:

- роль проверяется на сервере;
- финансовые поля отдаются только ролям `ADMIN`, `MANAGER` и `FINANCE`;
- бригадир видит только объекты своей бригады.

## Хранилище и очистка (экран администратора)

Требование команды, в ТЗ его нет: администратор видит, сколько занято, и сам чистит старые данные.

- **Заполненность:**
  - размер БД (`pg_database_size`) и крупнейших таблиц;
  - объём S3: всего, по типам файлов, по объектам, по месяцам;
  - свободное место на диске сервера.
- **Очистка фото (в первую очередь):**
  - фильтры: объекты в статусе «сдан» старше N месяцев, период, объект;
  - предпросмотр: сколько файлов и мегабайт освободится;
  - режимы: удалить оригиналы и оставить превью, или удалить полностью;
  - подтверждение и запись в журнал.
- **Прочее:** очистка прочитанных уведомлений и старых записей журнала старше N месяцев.
- **Сжатие на входе:** фото сжимаются на телефоне до ~1600px JPEG, на сервере создаётся превью ~400px.

| 1      | Авторизация и роли, схема БД, справочники (бригады, договоры, 2 шаблона этапов), реестр объектов с фильтрами       | Реестр и справочники          |
| 2      | Карточка объекта (ход работ, шахта, даты, документы, журнал), мобильный экран бригадира с загрузкой фото, расчёт % | «Назначил → бригадир отметил» |
| 3      | Сводка руководителя, правила «требуют внимания», уведомления, рекламации, финансы, экран «Хранилище»               | Сводка, рекламации, финансы   |

Начинаем локально. Сервер и деплой подключаем, когда заказчик выделит инфраструктуру.

## Решения без ответа заказчика

Заказчик занят, поэтому решаем сами и правим по обратной связи. Места в коде помечены `// TODO(заказчик): …`.

| Вопрос                | Решение                                                                                                                                                        |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Шаблон новостройки    | Копия шаблона замены. Администратор правит названия и проценты в справочнике                                                                                   |
| Остаток задолженности | `стоимость для заказчика − поступившая оплата`; если стоимость пуста — `сумма договора − оплата`                                                               |
| Видимость финансов    | `ADMIN` и `FINANCE` видят и правят; `MANAGER` видит; `FOREMAN` не видит                                                                                        |
| Отчёт генподрядчику   | Форма ФКР «Еженедельный отчёт об исполнении договора» из демо, 13 колонок                                                                                      |
| Объект                | Один объект = один лифт (подъезд). Дом с несколькими лифтами — несколько объектов                                                                              |
| Изменение процентов   | Пересчитываются все объекты, как в демо: процент берётся из справочника при каждом расчёте                                                                     |
| Отметки этапов        | Можно отметить сразу несколько этапов (пропущенные отмечаются той же датой). Дата — сегодня или до 7 дней назад. Отменить последнюю отметку может руководитель |
| Фото                  | Обязательно там, где в справочнике стоит флажок (сейчас везде), нужно хотя бы одно                                                                             |
| Поставка оборудования | `не заказано → заказано → поставлено`, плановая и фактическая дата                                                                                             |
| Контрольные даты      | Ставятся сами при отметке этапа (ПТО, комиссия, КС), руководитель правит вручную                                                                               |
| Рекламации            | Статусы `новая → на рассмотрении → принята / отклонена → закрыта`; поставщик — свободный текст с подсказками из прошлых значений                               |
| «Требуют внимания»    | Как в демо: срок прошёл; до срока ≤21 дня и <80%; отставание от линейного графика >20 п.п.; нет отметок ≥7 дней; нет бригады                                   |
| Хранение фото         | Без автоудаления. Администратор чистит вручную на экране «Хранилище»                                                                                           |
| Пользователи          | Логин на каждого бригадира, бригада привязана к бригадиру                                                                                                      |

## Как фронт получает типы API

Схемы запросов и ответов лежат в `backend/src/contracts/` — это чистый TypeScript + Zod, без импортов из Nest и Prisma. Backend валидирует ими запросы (`@Body({ schema })`) и строит OpenAPI. Frontend импортирует их через алиас `@contracts` — одни и те же схемы проверяют формы и описывают ответы.

## Фото и файлы

- Телефон сжимает фото до ~1600px JPEG и делает превью ~400px, загружает оба (`POST /api/files`, multipart).
- Файлы идут **через backend**, без presigned-ссылок: он проверяет права (бригадир — только свои объекты) и отдаёт файл из S3 потоком с долгим кешем. MinIO наружу не открыт.
- Отметка этапа ссылается на уже загруженные фото (`photoIds`). Фото, загруженные без отметки, — кандидаты на очистку на экране «Хранилище».

## Авторизация

Своя, без сторонних библиотек: логин и пароль (scrypt), сессия в httpOnly cookie, в БД хранится только SHA-256 токена. Глобальный guard закрывает все маршруты, `@Public()` открывает, `@Roles(...)` ограничивает по ролям. Вход ограничен по частоте (`@nestjs/throttler`).

## Открытые вопросы к заказчику

1. Шаблон «монтаж в новостройке»: этапы, проценты, обязательность фото.
2. Формула остатка задолженности и видимость финансовых полей по ролям.
3. Файл-образец отчёта генподрядчику и образец отчёта по объекту.
4. Шаблон Excel для импорта, реальные данные, количество объектов и пользователей.
5. Объект — это один лифт (подъезд)? Как считать дом с несколькими лифтами?
6. Изменение процентов в шаблоне: пересчитывать идущие объекты или фиксировать шаблон на момент создания?
7. Отметки этапов: можно ли отметить несколько сразу, кто правит и отменяет, разрешена ли задним числом.
8. Значения статуса поставки оборудования.
9. Статусы рекламаций; справочник поставщиков или свободный текст.
10. Пороги «требуют внимания». Пока берём из демо: 7 дней без отметок; до срока ≤21 дня при готовности <80%.
11. Хостинг, домен, SSL, тестовая среда.

Ответы ждём; до них действуют решения из раздела выше.
